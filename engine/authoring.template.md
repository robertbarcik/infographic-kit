# Authoring guide: sketchnote pages

> Generated by `node engine/list.mjs --authoring` from `engine/authoring.template.md`
> and the engine code. Do not edit `AUTHORING.md` by hand.

You write **content only**: a JSON spec in `specs/<name>.json`. The engine decides every
colour, size, font, position, outline and picture. Same spec in, same pixels out.

```
node engine/render.mjs specs/<name>.json    # render + measure one page
node engine/render.mjs --all                # every spec in specs/ (files starting with _ are skipped)
node engine/list.mjs                        # components, budgets, icons, roles (from the code)
```

Output: `out/<name>.png` (2480x3508), `out/<name>.pdf` (A4, 1 page), `out/<name>.html`,
`out/<name>.report.json`. Exit code 1 = the page is not acceptable; read the messages, fix
the **spec**, render again. Always open the PNG and look at it.

## 1. Content rules (every page)

1. One page = one idea. The title says the idea, not only the topic ("Protocols: agreed rules").
2. An everyday analogy carries the page (top section, usually `dialogue`), and the technical
   part maps back to it explicitly (the analogy's rules reappear as the key ideas).
3. A beginner can follow it; a practitioner still learns a precise fact: real commands,
   port numbers, real tool names in the examples.
4. Short, spoken sentences. No filler, no marketing tone, no "leverage / seamless / robust".
5. Every fact must be true. Simplify, never falsify. Use documentation values
   (`example.com`, `203.0.113.10`) rather than invented "real" ones.
6. The last row holds the closing strip: `callout` with `"variant": "remember"`, one sentence.

## 2. Spec skeleton

```json
{
  "title": { "number": "10", "text": "Protocols: agreed rules", "subtitle": "optional second line" },
  "rows": [
    { "sections": [ { "component": "dialogue", "label": "A conversation analogy", "...": "..." } ] },
    { "sections": [ { "component": "callout", "variant": "key", "text": "One key sentence." } ] },
    { "ratio": [5, 4], "sections": [ { "component": "layer-stack", "...": "..." }, { "component": "key-ideas", "...": "..." } ] },
    { "ratio": [3, 2], "sections": [ { "component": "exchange", "...": "..." }, { "stack": [ { "component": "definitions", "...": "..." }, { "component": "illustration", "...": "..." } ] } ] },
    { "sections": [ { "component": "callout", "variant": "remember", "text": "The one sentence to keep." } ] }
  ]
}
```

- A page is a vertical stack of **rows**; a row holds 1-3 **sections** side by side,
  widths by `ratio` (whole numbers, e.g. `[3, 2]`; default equal).
- A cell may be `{ "stack": [section, section(, section)] }`: 2-3 sections stacked
  vertically in one column (for "one tall section left, two small ones right").
- Every section: `component` (required), `label` (the tab; most components require it),
  `role` (optional semantic colour), plus the component's own fields below.
- Optional top-level `meta`: `{ "lang": "sk", "author": "...", "source": "...", "notes": "..." }`
  and `$comment` (ignored).

{{PAGE}}

**Forbidden anywhere in a spec:** colours, sizes, coordinates, fonts, CSS, raw HTML/SVG.
Keys such as `color`, `style`, `class`, `html`, `svg`, `font`, `size`, `width`, `height`,
`x`, `y`, `left`, `top`, `margin`, `padding`, `background`, `fill`, `stroke` are rejected.
If a page needs something the engine cannot draw, the fix is a new engine component or icon,
never a hack in the spec.

## 3. Text

- Inline markup only: `**bold**`, `` `code` ``, `->` (drawn arrow), and `\n` for a line
  break where a field allows 2 lines. `code` keeps its case even in capitalised labels and
  headings, and wraps only after spaces and `/ . ? & = , _` (never inside a flag like `-d`).
  A real command of more than a few words belongs in the `command` component, not in bullets.
- Bold is drawn with a thin outline so it shows in the handwriting font in every component.
- Budgets below are **maximum visible characters** (markup not counted). Staying well under
  them keeps the page airy. The layout check still fails a page if text does not fit the
  actual box (e.g. many cards in a narrow column), so budgets are necessary, not sufficient.
- Characters: Latin incl. all Slovak/Czech diacritics (ľ š č ť ž ý á í é ú ä ô ň ď ŕ ĺ),
  common punctuation, en dash. No emoji, no symbols outside Latin; write `->` for an arrow.

## 4. Roles (semantic colour)

automatically; set `role` on an item only when the colour must mean something.

## 6. Icons

{{ICONS}}

Pick the icon that shows the **thing** (device, document, action), not an abstract idea.
Two icons can be combined only in `exchange` actors (`["laptop", "database"]` = laptop
serving files). Missing a device? Ask for an engine icon; do not fall back to lucide for
core devices.

## 7. People (dialogue)

`a.look` / `b.look` (dialogue) and `person` (scene actors) pick from these enums; defaults:
A = short dark hair, green shirt; B = long brown hair, purple shirt; both standing. Vary them
across pages so the cast does not repeat.

{{CHARACTERS}}
- `holding`: any icon name; the person holds it up in one hand (passport, cloche,
  envelope, postcard, bookmark, key...). Not with `pose: "thinking"`.
- Speech bubbles: every bubble has a tail pointing at its speaker, steered around raised
  hands, props and other bubbles, and its outline takes the speaker's shirt colour, so who
  says what is clear at a glance. In a multi-turn dialogue (`turns`) the conversation sits
  between the two people and the intro + rules run full width underneath; the people grow at
  most 1.15x to match the conversation.

## 8. What the validator checks (the meter)

Before rendering (spec errors, nothing is drawn):
schema (unknown component / key / icon / role / enum value, missing field, wrong type),
forbidden styling keys, raw HTML, text budgets, list lengths, max rows/sections, the
remember strip in the last row, characters the fonts cannot draw, cross-field rules
(e.g. illustration edges must name existing nodes).

After layout (the page is rendered, then measured):

| code | meaning | typical fix |
|---|---|---|
| `page-overflow` | content taller than the page at type scale 1.0; the message says how many px and about how many lines to cut, and names the tallest rows | cut text or items; move a section to another page (see section 10) |
| `page-underfilled` | > 8 % of the page empty at the largest type scale and spacing cap; boxes are never inflated to fill | add content: a section, an example, a key sentence |
| `clipped` | a text/box sticks out of its container | shorten the text; widen the section (`ratio`) |
| `text-overflow` | a word or `code` cannot wrap and is wider than its box | shorten the code / URL, break it into words |
| `overlap` | two boxes/texts in the same container overlap | report as an engine bug if the spec is valid |
| `arrow-over-text` | a drawn arrow crosses a text | shorten labels; change illustration layout |
| `outside-page` | something lies outside the page | engine bug |
| `font-too-small` | text below 17 px | engine bug (the engine never goes below 17 px) |
| `missing-glyph` | the font has no glyph for a character | replace the character |
| `tail-over-person` | a speech-bubble tail touches a raised arm, hand or prop, or another person | shorten that bubble, change the pose, or move the prop |
| `tail-over-bubble` | a tail crosses another bubble | fewer or shorter turns |
| `tail-wrong-speaker` | a tail ends nearer to another person than to its speaker | engine bug if the spec is valid |
| `tail-too-short` | a tail is shorter than 14 px | engine bug |
| `bubble-over-person` | a bubble touches a person's head, arm, hand or prop | shorter bubble text, or no prop |
| `unbalanced-row` (warning) | one section in a row is much shorter than its neighbour | balance content or change `ratio` |
| `lucide-fallback` (warning) | a `lucide:` icon is used | fine for small details; request a kit icon for anything prominent |

Auto-fit: the engine scales all type, icons and spacing (`k` 1.0-1.4, body text 19-27 px,
smallest text at least 17 px), then stretches vertical gaps a little (`vs` 1-1.3). Callouts (goal, tip, remember, key)
always hug their content; the small remainder goes to rows with real content. A page that
still cannot be filled fails as `page-underfilled`. The report shows `k`, `vs`, body size
and empty space.

## 9. Picking the analogy component

- `dialogue`: two people talk (one line each, or 2-4 numbered `turns`) and a rules box
  names what they agree on. Best for "agreement / conversation" analogies.
- `scene` (= `exchange` with `actors`/`links`): a picture story of 2-4 actors in a row,
  each a drawn person (optional speech bubble) or an icon, with labelled arrows between
  neighbours. Best for "something travels from A via B to C" analogies (letter, waiter,
  phone book). Stack 2-3 scenarios to contrast (registered letter vs postcard).
- `exchange` classic form (`a`, `b`, `arrows`): the technical mapping, device to device.
- A person can carry the thing that travels (`holding`: passport, cloche, envelope...), so
  the analogy object is visible in the picture without an extra actor.
- Scene arrows take `step` badges (order of events) instead of "1." in the label text; a
  link `{ "versus": "or" }` draws a divider between two alternatives instead of an arrow.
- Technical pictures after the analogy: `illustration` `fan` for "one asks, the hub calls
  several in order" (DNS resolver: numbered `step` badges, `back` answers), `hub` with `side`
  for "one thing, many roles around it", `commit-graph` for history with branches.

## 10. Page capacity (plan before you write)

Measured at the smallest type scale (k = 1.0), full page width unless a width is given.
The page body is **1698 px**; the title takes about **75 px** (about **117 px** with a
subtitle); every row adds a **15 px** gap. Sections in one row take the height of the
tallest.

| section | typical height |
|---|---|
| callout, one line (goal, tip, remember) | 90-100 px |
| callout `key` (one sentence) | 50 px |
| callout with 2-4 bullets (half width) | 180-210 px |
| `dialogue`, one line each + 4 rules | 340 px |
| `dialogue` with 4 `turns` + 4 rules | 410-455 px |
| `exchange` / `scene`, 1 scenario | 260-300 px |
| `exchange` / `scene`, 2 stacked scenarios | 570-610 px |
| `exchange`, 3 stacked scenarios (60 % width) | 770 px |
| `steps`, 4-5 steps | 210-250 px |
| `card-grid`, 6 cards in one row | 270 px |
| `card-grid`, 7-8 cards (two rows) | 400 px |
| `card-grid` `compact`, 10 cards | 300 px |
| `key-ideas`, 3-4 cards (half width) | 330-420 px |
| `layer-stack`, 4-5 layers (half width) | 340-355 px |
| `compare`, 3-5 rows | 235-320 px |
| `definitions`, 4 terms (60 % width) | 240-260 px |
| `illustration` with a caption (half width) | 250-345 px |
| `bullets` / `command`, 3-4 items (half width) | 160-300 px |
| `commit-graph`, 2 lanes | 230-280 px |

Rules of thumb:
- A page holds about **1500 px of sections** (6 rows including the remember strip).
- The reference shape fits: analogy (350-450) + key sentence (50) + a two-column row (350-420)
  + a full-width row (250-300) + a half/half row (200-300) + remember (100).
- Two stacked-scenario analogies, or a 4-turn dialogue plus a 3-scenario exchange, do not fit
  on one page. Split the topic, or pick the lighter form.
- Commands: one `command` section is one terminal window, whatever the number of commands;
  `output` keeps its line breaks (up to 3 lines). Code of 24 characters or less never breaks.
- `commit-graph`: put `main` on the top lane; a tag's `was` shows where the pointer stood
  before (fast-forward).
- `layer-stack` `bracket` in a half-width section: the label goes above the bracket (range
  starts at the top layer) or below it (range ends at the bottom layer).
- If `page-overflow` asks for N lines, cutting one card row, one scenario or one bullet list
  is usually faster than trimming words everywhere.
